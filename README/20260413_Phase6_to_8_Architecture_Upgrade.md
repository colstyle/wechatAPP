# Phase 6-8: 架构升级与安全加固 (Architecture Upgrade & Security Hardening)

**日期**: 2026-04-13
**相关文档**: PRD (F23), PLAN (Phase 6-8), ENV

## 核心目标
将应用从“初期开发版”升级为“可交付准生产版”，通过多环境区分、数据资产安全管理、动静解耦、标准化工程目录等手段，彻底消除上线后可能产生的数据倒挂风险，保障业务可持续迭代。

## 关键技术成果

### 1. 业务护城河：快照与鉴权 (Security)
- **价格快照双轨制**：
  为防御“修改库房商品数据导致历史用户的押金/租金被连带篡改”的致命性业务 Bug，强制在 `order_items` 表新增了对商品当时交易环境的记录 (`snapshot_price`, `snapshot_deposit`)。所有退款及逾期的计算被重定向至快照副本。
  提供并运行了对应的 DB Migration 工具，完成了对旧订单的无痛数据回填。
- **动态 Token 校验 (Auth)**：
  后端登录由直接通过 `nickname` 获取伪随机 `openid`，变更为调用微信真实的 `jscode2session` 解析接口。建立针对全量 `/api/v1` 的身份鉴权和错误拦截中间件。后端剥离敏感 `.env`，彻底消除明文秘钥进入 Git 的可能性。

### 2. UI/UX 工业化：店主组件与静态解耦
- **独立权限视图的打通**：
  在 `pages/admin/orders`（店主大屏）实装了“库存管理”与“套餐管理”，打通了 CRUD 流。下架商品时提供关联安全保护拦截（硬删除退化为软删除挂起状态 `status=0`），防御因为外键或代码引用空指针导致的崩溃。
- **高频成本件数据解耦 (JSON 化)**：
  对于分类结构、固定套餐选项以及 AI 的 FAQ 快问快答库，实行 JSON 化并打包在前端独立目录 `frontend/data/` 挂载，利用本地执行来代替远端的 DB 请求。此技术直接让 AI 机器人实现“零 Token 发起常用咨询答复”，以提升商业上的 API 限额利用率。
- **自定义挂件 (Widgets)**：
  重封装 `cp-empty` 空数据保护罩与 `cp-countdown` 24小时超精细环形 CSS 进度指示仪，对全页面实施替换。

### 3. 工程整理与断舍离
- 重组微信端的网络层逻辑（剥离至专门的 `request.js`），支持动态注入多环境域名组合；
- 在后端利用 FastAPI 的 Middleware 能力完成全局的日志埋点 (`LoggingMiddleware`)；
- **废除僵尸代码**：大范围下架原型迭代早期留下的孤岛废文件包 (`taro-main/`) 和过渡期前端切图（`address` 等非 1.0 上线必须的无用路由）。

## 后续演进 (Next Steps)
此版本后项目基本具备发版封测的能力。后续的工作重点将转向 **Phase 9 (Git 联合发行)** 及自动化环境流转测试。
